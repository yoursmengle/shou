# Design

## Context

参见 proposal.md 的动机。本机 0.21.0 x64 的记录确认 13 个 Edge 文件共享冲突和 pip、uv、VS Code 的 3 个局部超时；17 个候选中有 7 个完整无阻断目标。Presentation 已支持 partial 批次中的独立完整候选，真正的全局阻断是 Platform 的固定关闭门禁。原生删除、确认、日志及取消服务已经存在。

## Goals / Non-Goals

**Goals:** 将原生 Windows 11 x64 的规则清理接入既有安全链路；准确解释部分覆盖；保持 GUI、CLI 和打包能力一致，以生成夹具证明所选目标删除与保留边界。

**Non-Goals:** 开放 ARM64、空间删除、隐私删除、卸载、启动控制或回收站；消除外部进程的真实文件锁；放宽所有者、权限、保护、清单、活动检查或扫描预算；安装发布或自动清理用户文件。

## Decisions

1. 保留现有广泛门禁关闭，新增仅规则清理的原生 x64 可用条件。App/CLI 普通规则入口采用该条件；执行前拒绝非规则计划，普通规则服务不注入空间变更能力。避免直接把共享开关改为 true，从而开放其他领域。打包回执的总体可用字段表示该文件清理能力组有公开执行能力，并增加精确的规则清理字段及原生主机限制；软件包升级属于已有的独立领域。
2. 复用当前 CleanupService、CleanupClickConfirmation 和终端确认，不新增批准文件、绕过参数或第二次 UI 确认。所选完整目标仍经过整批预检和逐项原生实时复核；CLI 非交互拒绝保持。
3. 不改变预算或文件共享策略。文件锁与局部超时是有效观察，应该阻断受影响目标；增加问题对应的说明和既有单位置重扫指引，不把 partial 改为 complete。单位置标题改用 scope 完成性及分析问题，和批次状态语义一致。
4. 错误说明保持一个可测试的 Presentation 映射，由 App 本地化呈现；新增文案只写 String Catalog 后运行生成器。用现有覆盖／底栏位置说明完整目标仍可选择，避免增加重复面板。

## Risks / Trade-offs

- 公开规则能力变化影响 CLI 和包元数据 → 一起更新能力合同回归，保留其他门禁关闭，并在执行前拒绝存储计划。
- 部分覆盖的源缺口可能被误判为执行失败 → 显示具体原因和局部重扫指引，保持目标资格与批次完成性分离。
- 普通用户的缓存可能属于其他所有者或含保护数据 → 如实保留阻断，不修改 ACL、不取得所有权。
- 本机仅有 x64 原生证据 → ARM64 保持不可执行，x64 单独构建、原生夹具和真实 WinUI 生成夹具闭环留证。

## Migration Plan

不改变持久化格式，既有快照和计划仍按现有版本与期限核验。先补回归，再完成能力、界面及文案更新；通过本机 x64 原生检查后交付构建。回退时恢复规则专用门禁关闭即可保留扫描与历史。打包脚本只验证元数据，不创建发行或覆盖安装。
